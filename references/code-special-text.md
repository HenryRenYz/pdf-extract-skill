# Code, formal grammar, and special text

Read this reference when you encounter program fragments, formal grammar, code with cross-line annotations, terminal output, genuine ASCII art, or code comparisons. The goal is to **establish a format specification supported by this book's source content and verify the implementation**; it is not to wrap every piece of code in the same monospace box. The body text and retrieval edition share the same verified content, structure, and style ranges. The existing [data contract](data-contract.md), [font workflow](typography.md), and [LaTeX export](latex-export.md) still apply.

## Confirm tool capabilities first

The main pipeline is wired to `semantic_contract.py`, `special_text.py`, and `export_latex.py`: it accepts `code/grammar/display_group` and supported Unicode style ranges, per-page validation/normalization/assembly preserves structural fields and source identity, and the exporter saves the original code as a UTF-8 asset with a hash; the rendered file is isolated from the original text so TeX characters in the program are not executed. Body text and retrieval share the same semantic version; passing type and provenance checks still does not mean the visuals or content are correct.

The current code path uses native external-file input via `fvextra/fancyvrb`; font size, font, line spacing, and block-level outer indentation are set by the template and the reviewed code_presentation, while inner indentation preserves the original lines. It supports original Unicode decoration ranges, Chinese text, the source tab policy, and soft line wrapping of ordinary code. **Cross-line annotations implement only a right-side brace, and annotated code must not soft-wrap**; left/top/bottom annotations and precise anchor mapping after automatic wrapping are not implemented and are rejected explicitly rather than silently dropped. The display-line mapping for soft wrapping still requires actual PDF inspection.

Grammar supports literal `grammar_lines` with indentation, measured prefix alignment and script positions, restricted safe syntax such as array/aligned in explicit native `latex/native_latex`, or literal `alternatives` with native stretchy brackets; it is not an automatic typesetter for arbitrary grammar ASTs. Grammar-level styles are not yet supported; decorations must be placed in explicit LaTeX or alternatives. A program comparison group uses 2..4 native minipage columns, each bound to a code_id or ordered paragraph/list/code/grammar block_ids, with optional caption_id and unique-consumption checks; when the source image requires the left and right captions on the same baseline, give the group `caption_alignment="bottom"`, and the renderer measures the actual height of each column's code with standard TeX boxes and aligns the captions, without adding blank lines to short program source. The default natural places captions according to each column's natural height. If source content is squeezed out or the group is too tall, PDF visual acceptance is still required; you cannot close the issue based on a successful compile.

Nested right braces for the same program may each bind a line range, and the annotation may be given `x_offset_ccwd` (-6..6) and `start_yshift_em/end_yshift_em` (-3..3) to describe source-supported anchor geometry; the defaults are 0, 0.45, and -0.35. The parameters do not change text lines or original inner indentation, and must come from review of the actual source region. Do not use the unwired `offset_ccwd` or force the same range to represent an entire function body.

`display_group` itself must have an independently source-reviewed `group_presentation` before it can consume candidate groups; an explicit `reading_order` must cover every code/caption exactly once. When an annotation references a separate `label_block_id`, that label belongs to that code and must not be laid out again at the top level or claimed by multiple annotations. Code, captions, and annotations within a group each retain their provenance mapping; when a line mapping cannot locate an independent TeX fragment, mark the `containing_group` instead of pretending to give an exact line number.

The page prompt has been updated to the new schema: models submit only structure/style candidates and unreviewed/uncertain evidence, and fabricating `review.source_checked` is forbidden. Only after an independent coordinator checks the real source image does it fill in the presentation's source/image/text hashes, `source_block_ids`, and the real evidence path/hash/reviewer. New books or new template production must pass the [artifact gate](book-format-preflight.md); a historical tool snapshot does not automatically grant the current main tool a passing status.

## Classification and body-text fidelity

| Content family | Preservation and rendering boundaries | What must not replace it |
| --- | --- | --- |
| Program code `code` | Preserve language, original lines, original characters, comments, source styles, and internal hierarchy; distinguish complete programs, fragments, pseudocode, and unknown provenance | Changing syntax to modern compiler conventions, adding missing brackets, or refactoring the program on the author's behalf |
| Formal grammar `grammar` | Preserve productions, optional items, repetitions, alternatives, terminal/nonterminal markers, and keyword decorations; model two-dimensional choice structures independently | Assembling tall braces from spaces and `⎧⎨⎩`, or treating all productions as ordinary verbatim |
| Code with cross-line brace annotations | Program text remains native text; annotations bind to real line ranges, endpoints, and labels | Converting the whole program and its Chinese comments into an image because one brace is hard to draw |
| Side-by-side code with captions | Build a comparison group, columns, independent code IDs, and an optional caption ID per column, and specify the reading order | Stacking all code vertically first, then outputting two centered captions together |
| Verbatim terminal output | Preserve the display conventions for prompts, output lines, whitespace, and control characters; transcribe only what is on the source page | Inferring or executing commands from the output, auto-highlighting, or replacing prompts |
| Genuine ASCII art | When the source content really draws with a character grid, preserve characters, rows/columns, and fixed cell width; confirm the original tab rules | Renaming failed typesetting braces, grammar diagrams, or block diagrams as ASCII art |

A "fragment" need not compile. Even a complete program is first transcribed faithfully; only when the language version and dependencies are known to be available and running is within the current job scope may compilation/static checks help find suspicious points; a check error does not authorize rewriting the book. Obvious misprints in the scanned copy and variant readings in the digital edition are recorded separately, and one version must not silently overwrite the other. Characters in code such as `—`, `−`, `-`, `*`, `×`, `λ`, `入`, full-width punctuation, and different quotation marks are checked only with support from that source range and the language semantics; a book-wide global replace is forbidden.

## Keep four kinds of position separate

1. **Original lines and intra-line indentation**: the code's own hierarchy or syntactic whitespace, especially in whitespace-sensitive languages such as Python. When the source uses a proportional font, what is observable is positional relationships, not an exact number of spaces; preserve relative hierarchy, the original bbox, and uncertainty, and do not fabricate "the source has four spaces".
2. **Block-level outer indentation**: the code's starting point relative to the body-text column boundary. Use template parameters such as source-reviewed `outer_indent_ccwd`; this is independent of leading whitespace. Body-text `parindent` does not automatically give Verbatim outer indentation.
3. **Display line wrapping**: soft wrapping introduced for the new paper width; it does not add or remove source line breaks and does not change the source file or line numbers. Preserve the mapping from original lines to display lines; if a continuation marker is needed, it is an explicit display aid and must not become a program character.
4. **Comments, labels, and decoration anchors**: right-side Chinese comments, circled step numbers, cross-line braces, underbraces, and keyword underlines are recorded independently; you must not use leading spaces in an ordinary TeX paragraph to pretend to preserve position.

Within a side-by-side group, apply these rules per column. For circled-number program explanations, first decide whether they are list/paragraph or code; the presence of `x+=1` does not make the whole group code. For source code spanning pages, first verify whether it is a continuation, then merge source lines and preserve provenance; a source page boundary is not automatic evidence of an original program line break or a new paragraph.

## Data standards that can be wired in

Create `book-code-special-profile.json` in the book workspace (the name may be adjusted to follow existing project conventions). Record at least: source PDF hash, rule version, actual source page/bbox and evidence hash, content family/language version, font family and Chinese/Latin mappings, font size/line spacing, outer indentation, inner indentation strategy, tab policy, soft-wrap policy, column and caption relationships, cross-line annotation policy, decoration ranges, packages used and template entry points, capability status, and real acceptance samples. Adopting a rule must not turn an `unreviewed` source block into `source_checked`; inferences about ranges and font families require separate evidence.

Every code block has at least a stable block ID, the original `text` and text hash, a UTF-8 original external file and file hash, source ID/page/bbox/hash, and source line range and numbering system. The external file is generated from the same semantic source and hash-verified; it is not a second body text to maintain. Known normalizations of original line endings/whitespace are recorded separately. Unicode half-open ranges in the semantic JSON and UTF-8 byte offsets must not be mixed.

A structure sidecar may describe, as needed:

- `content_kind`, `language`, `language_version`, `completeness=fragment|complete|pseudocode|unknown`; language appearance must not be used to confirm executability.
- Original `lines`/`source_line_ids`; the value, unit, and degree of source support for inner indentation; `outer_indent_ccwd`; `wrap_policy` and the mapping from original lines to display lines.
- Independent ranges for `font_family`, `weight`, `slant`, `emphasis`, and `decoration`. Kai is not slanted Song, and a keyword underline is not bold emphasis; when remaining compatible with existing `styles`, state the new field mapping explicitly and do not silently drop it.
- Grammar productions, choice rows, optional/repeated nodes, and literal and keyword ranges; if native math expressions are used, preserve a traceable token mapping to the source text.
- Annotation owner block, start/end line ID, start/end anchors, side, label block ID, and source bbox; cross-line start/end and original text ranges are verified separately.
- Group left/right column code IDs, caption IDs, source order, column weights, gap/separator lines, and whole-group pagination policy. Each source is consumed only once.

Original lines, code_presentation, annotations, groups, and Unicode styles have entered the shared schema; the richer `language_version`, arbitrary grammar nodes, or decoration anchors above remain design extensions, and the appearance of a field name in this reference does not mean the current renderer supports it. Actual limits are determined by the validation results of semantic_contract and special_text.

## LaTeX packages and the book template

When continuing this project's XeLaTeX setup, real code uses `fancyvrb`/`fvextra`'s native verbatim environments or external-file input by default; `fvextra` provides extensions to fancyvrb such as line wrapping. [fancyvrb](https://ctan.org/pkg/fancyvrb), [fvextra](https://ctan.org/pkg/fvextra)

Use native package settings and the template adapter to unify font size, line spacing, outer indentation, line breaking, Chinese fonts, and decoration. Ordinary code does not get line numbers, gray background boxes, syntax coloring, or "language labels" by default. When the original book already has these formats, implement them according to the evidence; when the user specifies otherwise, implement the specification and preserve the source content. Do not use a guessed tabsize common to all programs or a global dedent to erase the hierarchy of different content families.

Choose `listings` language-driven or style capabilities only when the source language and in-book style support them and real Unicode/Chinese-comment samples have passed verification. The package has default styles for keywords, comments, and strings; before use, override default behavior that disagrees with the original book. It is not an unconditional default that is more "professional" than verbatim. [listings](https://ctan.org/pkg/listings)

For two-line alternatives, upper/lower braces, and production alignment in formal grammar, prefer standard `amsmath` `array`/`aligned` and stretchy delimiters; literal text and language keywords go into the appropriate text/mono font ranges respectively. Distinguish `[...]`, `{...}` in the source from math delimiters and optional nodes; do not turn all grammar symbols into TeX commands; underline decorations and `_` in language identifiers must also be kept separate. [amsmath](https://ctan.org/pkg/amsmath)

Line-range annotations for complex code may use a TikZ overlay or a verified native box/coordinate layout, but the code and Chinese labels must remain selectable text, and the drawing only draws braces/connector lines. Fixed anchors are based on the final line baseline rather than copied directly from scanned pixels; re-check after wrapping, font size, or column width changes. Do not implement these annotations with character art or screenshots of the complete code. [PGF/TikZ](https://ctan.org/pkg/pgf)

External-file verbatim input avoids the body text hitting the environment terminator string or escaping-layer confusion, but you should still verify the file path/hash, provenance, and reference count. When rendering style commands is truly necessary, isolate the formatting from the original characters; choose a safe mechanism that does not conflict with the source and verify `%`, `#`, `$`, `_`, braces, backslashes, quotation marks, and TeX environment terminator strings, so the original code is not executed as TeX.

Chinese comments are actually trial-typeset through XeLaTeX's native CJK font support. Confirm this run's packaged font coverage, Chinese/Latin baselines, the choice of monospace versus proportional comments, and the actual glyphs and PDF text layer for circled numbers and special symbols; "the package is installed" or "compilation has no missing glyphs" cannot replace inspecting the final glyphs. Use local fallback only for specific characters with evidence, and record the original character, range, fallback font, and rendering result.

## Sample gate before batching

Choose representative source fragments from the **content families that actually occur in this book**; you are not required to invent types that do not exist. Have the same main renderer, the same template, and the final font package compile for real and compare figure by figure. Common acceptance combinations: Chinese comments and punctuation, whitespace-sensitive fragments, longer lines and soft wrapping, circled step numbers, cross-line braces, keyword underline, grammar alternatives, code/caption two-column layouts, and source continuations across pages.

Pass conditions include:

- Characters, source lines, style ranges, caption/annotation ownership, and source IDs/hashes are all preserved; decoration ranges agree with the source semantics.
- Inner indentation, outer indentation, soft wrapping, and column relationships are each explainable; comparison-group captions are under the corresponding column, and annotations point to the correct source line.
- Chinese and math/language symbols are actually legible; code text can be selected/searched from the PDF; the reading edition and retrieval edition come from the same source, and a change to one does not cause the other to drift.
- Package versions, template/renderer hashes, source screenshots, final screenshots, compile logs, character/range checks, and PDF positions are all recorded; the production status is explicitly `accepted`, and `proposed`, `pending_actual_pdf`, or `retained_source` must not be used to pass as final acceptance.

When the gate fails, first determine whether the problem is structural, character, font, or template related, make sample corrections within budget, and then decide whether to batch. If the budget is exhausted, the current renderer lacks a capability, or structural semantics are still lost, keep `needs_review` and list the affected block/source/final pages and the specific loss. If source-image retention is truly needed, state the range, reason, and impact on body-text retrieval/editability; it is a fallback pending review, not a lossless success. Do not turn all annotated code into figures in order to pass acceptance, and do not close these issues based only on page coverage, file hashes, and the end of LaTeX compilation.

Code symbols appearing in explanatory body text must also retain their literal nature: pointer expressions such as `*p+1` may use an explicit inline code role. A renderer compatible with legacy Markdown must not close emphasis with a pointer asterisk that follows another whitespace; such misparses are already rejected based on opening/closing delimiter adjacency to whitespace; this only prevents known parsing loss and cannot replace real code semantics. If a book-wide quick scan suggests treating a backslash operator as a missing function name or correcting an odd spelling in the source book according to common sense, source review is still required and the suggestion must not be adopted directly.

A reviewed comparison column can use either code_id or ordered block_ids (paragraph/list/code/grammar), with optional caption_id. Use the latter for real mixed steps-and-code columns. Preserve the explicit source reading order and unique ownership; absent source captions remain absent. The exporter calls the full block renderer for text/list columns. Native Kai and bold-italic font commands replace the old extra code wrappers; only width-preserving underline and annotation-anchor helpers remain shared body extensions.

Source color uses Unicode `styles` ranges with `kind=color`, `value=#RRGGBB`, and the usual evidence. Colors are literal source observations; the renderer does not run a language highlighter. For grammar that consists of literal lines, use `grammar_lines`: each row preserves `text`, optional additional `indent_em`, and ordered disjoint `scripts` ranges (`start/end`, `position=superscript|subscript`). Joined row text must equal the original text. Whitespace is emitted as native explicit spaces, and script position is independent of the literal character. Use reviewed native math for richer structures; do not rely on ordinary TeX spaces for alignment.

For alternatives aligned to an earlier production, a row can declare `align_to={line:<earlier 0-based row>,offset:<Unicode prefix length>}`. It measures the prior plain row with native `phantom`, replacing the current row's raw leading-space indentation only in the rendered view; the raw text is unchanged. `indent_em` adds an optional measured adjustment. Anchors target unscripted, unanchored rows, preventing recursive or ambiguous width calculations.
