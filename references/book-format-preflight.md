# Book format standard and template preflight

Use this when starting a new book, reusing an old template, or revising global formatting. Freeze verifiable in-book rules first, then expand body-text and figure jobs; read-only whole-book overviews, sample selection, source-image preparation, and a small amount of OCR can proceed in parallel beforehand. Do not start whole-book typesetting production calls before the typeset-mode template passes; extract/proofread can run independently. For the structure, package choice, and acceptance of code and special text, see [Code and special text](code-special-text.md).

## Selection and capability preflight

If the user supplies a template, use it; otherwise build a neutral template for the current document, without routine follow-up questions. Keep an existing explicit choice. Even a supplied template must be verified against the current source book; do not treat an old book's fonts, centering, font sizes, or list parameters as facts about the new book.

Inventory the typesetting families that occur in the source book, distinguishing at least numbered chapters/sections/subsections, local headings, labeled lists, ordinary paragraphs, inserted display formulas, real code, formal grammar, annotated code, and figures. Record only categories that exist in the source book. A table of contents does not reveal every local level, and bold text does not necessarily mean a heading. Check capability with the exporter, template, and dependency versions actually executed now: support in an in-book script or a historical tool-snapshot does not mean the main tool supports it.

Freeze the rules file, prompts, templates, exporter, and package versions together into the job input. If export capability must be added, implement and accept it on real samples first, then expand the job; never downgrade an unknown category to an ordinary paragraph or an image to pass type validation.

## Information the in-book rules must cover

The workspace stores `format/book-format.json`, recording the source PDF hash, rule version, template/exporter/prompt hashes, evidence from representative source pages, and the rules listed below that this book actually uses. It is the coordinator's run contract; `format_preflight.py` actually loads it, verifies the source hash, and resolves the template directory; describing a rule does not make it execute automatically. The API returns supported_template_keys/supported_template_rules to make explicit which fields have a template entry point; fields not wired in are still only descriptions; never save the JSON and then claim the capability is complete.

| Category | Frozen content and source review |
|---|---|
| Headings | Document parent-child structure, numbering pattern, difference between local ordinals and body-text steps; each category's font-size ratio to body text, font, alignment, spacing before and after, first-line indent, and table-of-contents inclusion policy. A local "1." or "(1)" must not be promoted to a section by default; unnumbered subheadings must not all be assigned the same heading_depth. |
| Body text | First-line indent of a genuinely new paragraph, continuation lines/continued sentences, display formulas inserted into the same paragraph, cross-page continuation, paragraph relationships inside proofs/examples. Pagination, OCR block boundaries, and formula block boundaries are not paragraph boundaries. |
| Lists | ordered/unordered/description/steps, with marker and label text separated; marker size/baseline, labelsep, the width of the Chinese-character space after the label, nesting level, outer indent, hanging indent, and continuation-line alignment. Do not express physical spacing with ordinary spaces, and do not turn every list into itemize. |
| Fonts | Keep semantic emphasis, font family, upright/italic, weight, and decorations such as underline separate; a style span covers an explicit range that may mix Chinese, Latin, and punctuation. If a Chinese italic in the book is actually Kai, map it to the real Kai; handle math italic and Latin fonts separately; never globally replace all italic with the same font. |
| Punctuation | Set rules separately for body text, formulas, code, strings, and numbering labels; keep verbatim recording separate from reading-edition normalization. A scan cannot prove Unicode full-width/half-width code points; a visually identical mark must not receive different spacing because OCR produced different code points. Preserve evidence for genuine exceptions or ambiguity in the source book. |
| Code/special text | The categories used in this book, language/dialect, native environment, packages, outer indent, inner indent, continuation/side-by-side relationships, fonts, decorations, and annotations; see the code reference for details. |
| Figures and tables | Classify as native text/math/code first, then decide the image route; freeze size, line width, arrows, label style, and backend per category. The content, topology, and special layout of each figure/table are still reviewed independently. |

## Boundaries for handling paragraphs and punctuation

Per-page output must retain candidate relationships: source-paragraph identity, whether the current block is a new paragraph or a continuation, whether a display formula shares a paragraph with what precedes or follows, cross-page predecessor/successor, evidence or uncertain. Keep each block's text, Unicode style spans, and sources independent; the reading layer can combine segments of the same paragraph, without forcing a formula into one giant string.

During aggregation, review adjacent blocks on the same page, the text before and after formulas, and cross-page boundaries together. Decide from the heading/list parent node, original first-line position, sentence ending at the line end, next-line position, and context; semantic guessing or looking only at punctuation must not confirm automatically. Every display-formula-to-text boundary must be explicitly same_paragraph/new_paragraph/uncertain; uncertain enters centralized review and does not start a new paragraph by default. Allow cross-page list items or proof continuations, retain the original marker and style, and merge only semantic units confirmed to be the same.

Export uses the reviewed paragraph relationships uniformly to generate separators, applying the same policy in body text, footnotes, narrow columns, and side-by-side groups. Do not insert a TeX blank line after a display formula that continues a paragraph; preserve natural breaks for genuinely new paragraphs. A logical new paragraph and a first-line indent are also two separate properties: when source review confirms a new paragraph but there is no first-line indent, keep the paragraph and use the standard noindent for that paragraph's role; do not force a merge merely because there is no indent. Never use a global noindent or per-page manual negative spacing to hide semantic mismatches. The physical spacing of a display formula is still controlled by the template; accept the two separately.

Code/strings/verbatim output preserve characters; math uses standard LaTeX syntax and explicit text punctuation; body text and structural labels are rendered per the book's reviewed rules. Do not run NFKC or global bracket/comma replacement on the whole book: it would change program literals, mathematical meaning, or source-book exceptions. Reading-edition normalization must record the original character, target representation, role, rule version, and source text hash; the verbatim layer stays unchanged.

Inventory the labels of the same definition, list, or proof across pages by semantic group; do not compare characters on a single page only. Mixing ASCII (n) with full-width （n） must be unified in the reading layer via explicit label_normalizations after source review; it must not be skipped even if every single page passes. Rearrange four items from the same group onto one page to check the actual brackets, digit font, starting position, and labelsep; brackets in code/strings do not participate in this normalization.

## Real samples and admission

Choose a small number of real regions that cover the typesetting families actually used in the book, and keep held-out pages. Samples should include adjacent headings of different levels, lists with short labels, negative examples of continuation paragraphs versus genuinely new paragraphs before and after formulas, cross-page continuation within a word, and, where the book has them, code/grammar, mixed fonts, underline, and side-by-side comparison. Do not use only invented tidy text, and do not check only the first three levels of the table of contents.

The coordinator generates a pilot-typeset PDF, actually inspects paired source/product regions, and iterates the template and structure mapping. Use standard packages and parameters: ctex controls real heading categories; enumitem handles list geometry; xeCJK/fontspec handle Chinese fonts and punctuation; code and grammar are chosen per the dedicated reference. Passing a small sample only proves that this typesetting family works; it does not prove that whole-book recognition is correct. Sample fixes must be written back into the actual production blocks/presentation, retaining a "source block → sample decision → production structure → final TeX/PDF" reconciliation list; if only the pilot script changes while the whole book still exports the old blocks, the issue must not be closed. Math aligned derivation groups and left-side step numbers should be verified separately; do not mislabel a display_group that supports only side-by-side code as supporting all math groups.

`format/template-ready.json` must contain at least the identity of this book and its rules, the identity of the actually executed tools, tested source blocks/output pages, the final PDF hash, each acceptance result, unresolved items, and the reviewer. Admission requires: every typesetting family actually used has a passing sample; there is no known structure/style loss; source-supported heading parent-child relationships, label spacing, list indentation, code annotations, underline, and paragraph relationships pass. A successful compile does not replace these checks. If they are not met, keep preflight/needs_review and only continue fixing samples or handle the limitation explicitly accepted by the user.

By default, preflight allows at most 3 rounds of local revision, within the current budget; at the limit, save the specific problems and do not create a pass mark just because 3 attempts were made. A rule change publishes a new version and re-verifies the affected categories before resuming batch jobs.

## Dispatch, final review, and known losses

Workers receive the frozen rules and positive/negative examples and do not change font sizes, whitespace, punctuation, or code packages on their own. Per-page recognition saves structure candidates, and chapter aggregation reviews continuity relationships; after local render self-check, an independent coordinator performs the final review. There is only one template/rules owner, and body-text and figure jobs submit mutually exclusive patches.

The final review separates coverage/compilation/linkability, content, structure, and detailed typesetting. Full-page overviews are for inventory and finding major problems; they must not close detailed issues such as font spans, underline, paragraph indentation, or program alignment. Inspect source/product comparisons at actual reading scale by typesetting family, and inventory all instances of that category and the risk scope; after a template fix, check the affected instances; for unchanged pages, reuse the completed review with same-parameter pixel-identity evidence.

Known underline loss, cross-page word breaking, code turned into a block figure, incorrect heading parent-child relationships, and misattributed annotations/headings are known format or structure losses; they must be fixed, fall back with source support, or be listed as explicit failed items. Do not put them into ordinary uncertainties and still claim broadly that "typesetting passed". Source-package portability, correct hashes, and complete page coverage are independent conclusions.

## Executable artifact admission contract

`load_format_profile(path, source_sha256)` reads and returns metadata, or raises ValueError. The profile must contain schema_version=1, source_sha256, a non-empty version, status=draft|frozen, the actual template_dir (relative to the profile file or absolute), and non-empty, unique representative_pages (PDF physical page integers) and tested_families (the typesetting families actually used in this book). The directory contains either the legacy `book-template.tex`/`book-style.sty` pair or a `template.json` project with its real entry and declared resources; see [template projects](template-selection.md). The current entry points of `template_rules.code` include font_family/font_size_pt/line_spacing_pt/outer_indent_ccwd; other rules remain descriptions and must not be passed off as automatic implementation.

`check_template_ready(profile_path, ready_path, source_sha256, tool_paths=None)` admits only a frozen profile and a ready with schema_version=1/status=accepted, and actually verifies:

- source_sha256 matches the original PDF, profile_sha256 equals the current profile file hash, and ready.template_dir matches the real directory resolved from the profile; template_files records the current hashes of the legacy pair or all native project resources plus template.json. Native projects also require template_dependencies from the actual recorder, with package-relative or environment paths and hashes; the gate verifies the dependency files.
- tool_sha256 records the hashes of all actual tools in `format_preflight.DEFAULT_TOOLS`, computed automatically from the current code's transitive local imports, including real dependencies for table of contents, figures and tables, document parts, and provenance identity; do not copy a historical six-tool list and miss real render dependencies. tool_paths may use a mapping to specify the actual executed tool paths, and may add extra tools; all must have a findable file and a matching hash. A self-reported hash for an unknown tool with no actual path is rejected. The optional prompt_sha256 also freezes the current page-prompt.txt/style-prompt.txt.
- compiled_pdf={path,sha256} must be an actually openable, non-empty PDF; not merely "compiled=true". checks is a list of unique name/status=pass entries, at least compile/source_fidelity/family_coverage; family_coverage.families covers profile.tested_families.
- Each source_checks entry contains page, output_page, status=pass, a non-empty reviewer, and evidence={path,sha256}; evidence must be a real readable source image/PDF, the output page must lie within the actual product PDF, and all representative source pages must have records. unresolved_issues must be empty. The reviewer is responsible for the truth of the correspondence between evidence and source content; the gate does not replace independent visual judgment.

ready paths are all relative to the ready file or absolute. Hashes must be genuinely computed; copying example strings, empty JSON, or automatically writing accepted for an unreviewed sample is prohibited. After a change to the source, rules, template, tools, or prompts, publish new actual evidence and ready; an old PDF's pass status cannot be reused.

```python
from scripts.format_preflight import load_format_profile, check_template_ready
profile = load_format_profile('/absolute/work/format/book-format.json', actual_source_sha256)
admission = check_template_ready('/absolute/work/format/book-format.json',
                                 '/absolute/work/format/template-ready.json', actual_source_sha256)
```

A typeset-mode page queue making production model calls must have `--format-profile ... --template-ready ... --execute`; export production uses the same admission. To create pilot-typesetting evidence, use `--format-profile ... --preflight-mode`, with at most 8 **actually selected source pages**, which may come from any chapter of the book; do not restrict physical page numbers to 1..8. This mode is non-production and must not be expanded to the whole book to bypass ready; the current source must still be bound to the profile. extract/proofread do not need template admission. When a page queue has no execute and only prepares, missing/incorrect gates record diagnostics without blocking and do not produce a pass mark. `--no-preflight` skips only the single-page CLI structure preflight; it cannot skip template admission.

The recovery contract of run_page_jobs freezes the profile/ready, the actual prompt, and the semantic/special/gate tool hashes; a change requires a new run directory, does not modify the contract of a historically completed queue, and does not require repeating old OCR on that basis. Template revision mainly reuses existing semantic data for pilot typesetting and acceptance.

## Render configuration and environment identity

The profile may contain render_configuration, with fields matching format_preflight.RENDER_DEFAULTS, covering paper, type area, figure size, fonts, and engine; fields not given use neutral defaults. ready must record the actual returns of render_configuration(profile) and render_environment(profile). The latter freezes Python/PyMuPDF/Pillow, engine identity, and hashes of font files obtainable from the system. If the actual CLI override differs from the frozen profile, production export refuses it; pilot typesetting may adjust it, but before formal freezing you must write it back into the profile and re-verify. Additional fonts/packages declared directly by the template must be confirmed through this environment inventory and samples; do not call the tool's limited environment check a complete TeX dependency lock.
