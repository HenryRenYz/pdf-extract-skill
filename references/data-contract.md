# Data contract and tool parameters

## Working directory

```text
book-work/
  source.pdf                 original file or read-only reference
  prepared/manifest.json     source hash, physical pages, image dimensions, tile coordinates
  prepared/input/0001/       original page, overview, tiles, and uncertainty crops
  raw/model/page.*           immutable native OCR
  typography/rules-v*.json   reviewed, frozen rules and provenance for this book
  typography/patches/        style patches and run records from independent font jobs
  jobs/model-page-attempt/   isolated session, input snapshot, revisions, run records
  corrected/pages/           verified per-page Markdown and JSON
  book/chapters/             merged reading edition
  book/images/               verifiable redrawn figures and source image crops
  book/blocks.jsonl          AI retrieval chunks with chapter, page number, and bbox
  book/review.json           items needing review and errata
  reports/                   quality, elapsed time, and cost
```

Create directories according to the actual job; do not pre-create empty placeholders. The skill tools do not provide a unified inference SDK for all models, and they do not generate a whole book automatically; model adaptation, batch job scheduling, image extraction, and merging are performed by the agent using the skill, following the workflow.

## Image manifest (generated by tools)

While preparation is in progress or has failed, the new tools publish only `progress.json`; they atomically publish `manifest.json` only after all requested pages are prepared successfully. The manifest contains `preparation_status="complete"`, `requested_pages`, and `completed_pages`; all three must be consistent with the set of physical pages in the `pages` list. When a single-page job copies the manifest, `requested_pages`/`completed_pages` are limited to that page, and `source_requested_pages` preserves the parent job's range. For manual or historical manifests that lack a completion status, you must not claim full-range completion based on file existence; verify explicitly with `--expected-pages` at the end.

Manifest paths are rooted at the directory containing the manifest; physical pages start at 1. Each entry in `original` and `images` contains `path`, `kind`, `width`, `height`, and `sha256`. `kind` is `original`/`overview`/`tile`/`crop`. `images` are the attachments the assigned model must view; `original` is retained for provenance, and you are not required to use the large full page as body-text recognition input.

`source_bbox=[x0,y0,x1,y1]` uses source image pixels, origin at top left, right/bottom endpoints exclusive. Tiles/crops are not scaled; map their coordinates as `(x+x0,y+y0)`; an overview bbox refers to the whole source page, so convert overview coordinates by the width/height ratio. PDF point coordinates and normalized bboxes must be converted explicitly first; the rendered image after page rotation is the coordinate basis for this manifest.

```bash
python scripts/prepare_images.py --pdf /absolute/book.pdf --pages 1-25 \
  --output /absolute/work/prepared --dpi 96 \
  --max-pixels 1526400 --max-edge 1908 --tile-height 800 --overlap 128
```

These dimensions come from the 1908×2445 page image example in this run; replace them according to the actual model limits and source scan. For native page images, use `--pages-dir /absolute/pages`; file names are numeric PNGs such as 0001.png. For extra crops, pass a list with `--crop-json`, for example `[{"page":18,"bbox":[100,200,800,500]}]`. The tool does not overwrite existing targets; a directory left behind by a failure is a partial artifact; inspect it or switch to a new directory and retry.

## Pages and blocks

A page has at least the following fields:

```json
{
  "page": 18,
  "printed_page": "4",
  "blocks": [{
    "id": "p0018-b001",
    "type": "paragraph",
    "text": "误差分析",
    "bbox": [100, 200, 800, 500],
    "styles": [{"start": 0, "end": 2, "kind": "bold", "evidence": "source_checked"}],
    "evidence": "source_checked"
  }],
  "uncertainties": [],
  "changes": [],
  "viewed_images": ["input/0018/overview.png", "input/0018/tile-001.png"]
}
```

The example text, coordinates, and page numbers only illustrate the fields. Actual `viewed_images` must contain the relative paths of all manifest `images` for the assigned page; do not copy the sample above. In a single-page job, the manifest moves to `input/manifest.json`, and the paths are `0018/overview.png` accordingly.

`type` can be heading/paragraph/formula/table/figure/caption/theorem/proof/example/exercise/header/footer/list/code/grammar/display_group/blank; `text` preserves readable text or LaTeX/table content. Every block has a stable ID. After merging, add `chapter_id`, `parent_id`, `number`, and `cross_refs`; these must not be guessed automatically from physical page offsets.

`semantic_contract.py` defines the shared enums and structural metadata; validator/canonicalizer/assembler/renderer use the same contract. The original text, original lines, and styles of code enter both the retrieval and reading layers; export generates one raw UTF-8 asset and an isolated render file, keeping each hash. `special_text.py` supports range decorations, native formal grammar, and side-by-side code groups; for the exact supported scope, see [Code and special text](code-special-text.md); unsupported annotation positions or grammar styles are rejected explicitly and must not be bypassed by downgrading the type.

For paragraphs and local headings, first determine the role/relationship according to [format preflight](book-format-preflight.md): physical pages, OCR blocks, and formula boundaries do not automatically become paragraph boundaries; local `1.` and `(1)` do not automatically become sections. Source paragraph continuations, logical new paragraphs, and first-line indents are stored separately, then reviewed together in aggregate. Role/style extensions are not just adding fields to JSON; the actual export behavior and trial-typesetting results must be verified together.

In `styles`, `start`/`end` are **Unicode character** indices into `text`, with `end` exclusive; they are not UTF-8 bytes and not JavaScript UTF-16 indices. `kind` is normal/bold/italic/bold_italic/upright/bold_math/double_struck/underline/kai/monospace/color; bold italic is separate from bold; `bold_math` is reserved for compatibility records of explicit mathematical bold that do not further distinguish glyphs, and must not be used to erase known slant differences. Math macros and `styles` should stay consistent; empty `styles` means styles were not recorded and does not prove that the whole block uses a normal font.

Block `evidence` remains unreviewed/source_checked/uncertain and states the basis for content recognition. Style `evidence` additionally allows `rule_inferred`, which must carry a non-empty `rule_id` and `rule_version`; a style inference must not be turned into whole-block body-text confirmation. A model-reported `source_checked` still requires human/independent source-image verification. The optional `rule_source_pages`, `rule_source_bbox`, and `rule_source_sha256` preserve the rule provenance; keep them distinct from the actual page/bbox of the block where the style appears.

For example, a local style whose content has been verified and whose font is inferred from a rule:

```json
{"start":0,"end":2,"kind":"bold","evidence":"rule_inferred",
 "rule_id":"B01","rule_version":"book-fonts-v1"}
```

The validator checks style kind, range, evidence, and rule ID/version fields, counts style evidence, and flags inferences not yet confirmed against the source image. It does not check the authenticity of rule files, rule applicability, patch merging, or actual glyphs; the calling agent verifies these according to the font workflow. Missing fields, forged rule confirmation, or unknown styles must not be concealed by "structure passed".

When bbox cannot be located, it is null and must be listed for review; do not fabricate coordinates. Each `uncertainties` item has `block_id`/`reason`/`bbox` and may add `observed`/`candidates`; `changes` has `block_id`/`before`/`after`/`reason`/`bbox` and may add `source_image`/`model`/`request_id`. Figure blocks may add `crop_path`/`caption`/`labels`/`reconstruction_method`; tables may add `cells`/`rowspan`/`colspan` and independent ruling-line candidates; preserve richer source data without losing the SDK's original fields.

Layout is not inferred from whitespace characters, HTML `th`, or Markdown tables. The final semantics may attach `inline_label` (structural label Unicode range, original whitespace end, `gap_ccwd`, original text/source hash, reviewed in-book rule ID/version), `table_layout` (source page/text hash, grid dimensions, horizontal/vertical single and double lines on half-open boundary ranges, and actual review), and a separate `figure-layout-decisions.json` (source-supported side-by-side or text–figure left/right relationships, stable figure/caption/complete-paragraph IDs, and multi-page provenance). Candidates must not be marked as verified directly; verify independently before export. For fields and helper APIs, see [LaTeX export](latex-export.md).

`bold` in normal text is a semantic emphasis tag; its actual glyphs are mapped by the book template, and the specific Chinese font mapping is specified by the current document template. Keep exact weight/font family separate from semantic emphasis, and do not let this mapping affect math macros such as `bold_italic`/`bold_math`. A new book may use a different explicit font mapping.

A separate `covers.json` stores the user's choice, explicit physical page roles, source hash, native page asset hash/dimensions/rotation, or field-by-field verified metadata for covers. A source-image cover may generate a whole-page proxy block with `type=figure`, a `cover` field, and `provenance.transcription:false`; it is retained source-image evidence, not OCR confirmation, and you must not fill in `viewed_images` that the model did not view. The body page range and the cover range together cover the current requested range; when the back cover is outside the range, do not output it.

```bash
python scripts/validate_outputs.py --manifest /absolute/work/prepared/manifest.json \
  --output-dir /absolute/work/corrected/pages --expected-pages 1-25 \
  --report /absolute/work/reports/structure.json
```

Exit code 0 only means structure, hashes, files, and self-reported coverage passed. It does not check math rendering, the actual input received by the model server, body-text semantics, whether blocks missed lines, or whether styles are correct; verify these separately according to the evaluation rules. Markdown image relative paths are based on the containing .md file; when moving/merging, rewrite and re-verify them.

## Font patches

A rule file stores `source_sha256`, `version`, `fit_pages`, review status/records, and `rules` with `id`/`scope`/`examples`/`exceptions`; before applying, verify that it is the same book and that the version has been reviewed; rules of unknown provenance must not be migrated directly. Rule scope is limited by chapter/semantics.

The font job input `input/page.json` is a snapshot of proofread blocks, with `input/rules.json` attached. The calling agent computes and provides `base_text_sha256` from the UTF-8 encoding of each block's `text`; the rule model only returns values. Independent output uses the following structure; for the exact prompt, see `assets/style-prompt.txt`:

```json
{
  "page":18,
  "source_sha256":"source PDF hash",
  "rule_version":"book-fonts-v1",
  "patches":[{
    "block_id":"p0018-b001",
    "base_text_sha256":"SHA256 of the input block text",
    "styles":[{"start":0,"end":2,"kind":"bold","evidence":"rule_inferred",
               "rule_id":"B01","rule_version":"book-fonts-v1"}],
    "uncertainties":[]
  }]
}
```

Every assigned block has a patch; unknown styles may be empty and listed in `uncertainties`. The merge program/agent verifies provenance, version, original-text hash, block ID, ranges, and existing source-image confirmation, and keeps the text content unchanged; style changes are written to `changes` with provenance, and unknown items are merged into page `uncertainties`. If the text's indices change after rendering Markdown/LaTeX markup, recompute the ranges or store a mapping. A patch is not a complete page; you must not use `validate_outputs.py` directly in place of merge verification; verify the merged complete page afterwards. For the specific strategy, see [Font calibration](typography.md).

## Usage normalization

`account_usage.py` takes a JSON list as input, with one unique id per request:

```json
[{"id":"request-001","input_uncached":1000,"cache_read":2000,"cache_write":0,
  "output":300,"reasoning":100,"actual_cost":null,"currency":"USD","partial":false}]
```

`output` already includes `reasoning`. Use null for unknown counts/costs; fields that have a count must be non-negative integers. Summarize multiple currencies separately. Keep actual cost and price estimates in separate columns; `actual_cost_complete` only means every listed request has a cost, not that the ledger covers all requests; `usage_partial` independently indicates that usage is incomplete.

The price file explicitly provides `currency`, `as_of`, and `per_million` (the four unit prices `input_uncached`/`cache_read`/`cache_write`/`output`); do not hard-code current unit prices in the skill. Use Decimal for exact budgeting. Write 0 explicitly for fields that are free of charge; unknown prices must not be counted as free.

```bash
python scripts/account_usage.py --records /absolute/work/requests.json \
  --prices /absolute/work/prices.json --output /absolute/work/reports/cost.json
```

## Whole-book export

The default reading delivery uses LaTeX; body text and retrieval data are exported from the same verified per-page JSON. Optional Markdown/HTML is derived from the same JSONL; do not maintain a separate body text. `assemble_book.py` generates only `source-blocks.jsonl`, `blocks.jsonl`, and `assembly-report.json`; it does not generate default Markdown/HTML/README, does not copy full-page images, and does not call models.

```bash
python scripts/assemble_book.py \
  --manifest /absolute/work/prepared/manifest.json \
  --pages-dir /absolute/work/canonical/pages --expected-pages 1-50 \
  --source-pdf /absolute/current-source.pdf --output /absolute/work/book \
  --figures /absolute/work/book/figures.json \
  --merge-decisions /absolute/work/reviewed-boundaries.json
```

You may also use `--jobs-dir /absolute/work/page-jobs` instead of pages-dir. Job input accepts only the **latest validated checkpoint** for each page; it verifies the producer contract's provenance/model/range, the complete file hash list, the actual single-page image, and the current prepared image hash, then runs structural validation. It does not silently fall back to an earlier successful attempt. The final image manifest must fully match expected-pages, and the current PDF and native image hashes must agree.

The normalized `--expected-pages` is the actual output range for this run and may be a subset of a page job's `contract.expected_pages`; every consumed page must belong to that producer's `owned_pages`, and all owned pages must be within the producer's range. Multiple mutually exclusive shards may be aggregated, but exactly one producer must correspond to each page. Read-only context pages may be in the producer range but outside the canonical output range; the normalized manifest contains only output pages, and source image hashes must still match each job's attachments. When extending an existing manuscript, verify/retain overlapping pages only once, keep accepted semantic blocks and footnote/source-review metadata, and do not fall back to an earlier raw or canonical copy.

Canonical input uses `canonical/manifest.json` or `canonical/pages/manifest.json`. It contains at least `source_sha256` and a `pages` list covering the complete page range; each record is:

```json
{"page":1,"json_path":"pages/0001.json","sha256":"SHA256 of the final canonical JSON",
 "input_json_path":"/absolute/page-job/output/0001.json",
 "input_json_sha256":"SHA256 of the unmodified raw model JSON",
 "normalization":{"description":"deterministic normalization reviewed in this round"}}
```

Each canonical page object additionally keeps `source_sha256` and `source_image_sha256`, verified against the current PDF and prepared source image. The original normalized input files are still retained with verified hashes; path-representation adjustments, type adaptations, and similar changes are recorded in a separate log; you must not secretly alter body text or pass a revised file off as raw model output. A hash here proves artifact identity, not content accuracy.

`source-blocks.jsonl` retains every source block, including header/footer; the reading body text in `blocks.jsonl` excludes header/footer, and every other source body block maps to a reading block exactly once. Each entry keeps `block_id` (the original id), `parent_id`, `chapter_id`, `page`, `printed_page`, bbox, text/text_sha256, styles, and the raw-input and normalization provenance. A model-reported body-text/style `source_checked` is downgraded to `unreviewed` and preserved in `model_evidence` and the report; independent boundary confirmation does not upgrade whole-text evidence.

Chapters are identified by actual chapter number, title, and table of contents/preface/publication information, not by fixed page ranges for a particular book. A chapter is depth 1, a numbered section such as 1.1 is depth 2, and a subsection 1.1.1 is depth 3; the original text is not changed. `chapter_id` uses chapter-N, front-publication/front-prefaces/front-contents; parent refers to the original heading block. Hierarchy is marked `structure_inferred`; content and font evidence are independent. A chapter entry inside the table of contents must not become a new body chapter; structure that cannot be determined is listed for review.

A reading block's `sources` stores at least each original block_id/page/printed_page/bbox/source_sha256/source_image/source_image_sha256/text_sha256. `source_image` is the real prepared source image path relative to the book output root; `source_image_absolute_path` is stored separately; full-page images are not copied. A combined block keeps `source_block_ids`, `pages`, `source_styles`, and the provenance of each item; the overall bbox for multiple pages is null, and you must not fabricate a single cross-page coordinate. Per-page original text always remains in source-blocks and the original page JSON.

Automatic cross-page detection only produces candidates; it does not merge automatically. Applied `merge-decisions` must come from actual source-image review, for example:

```json
[{"left_block_id":"p0010-b020","right_block_id":"p0011-b001",
  "action":"merge","source_checked":true,"source_sha256":"current PDF hash",
  "reason":"Viewed the source images of the two adjacent pages and confirmed the truncated continuation sentence","separator":""}]
```

The actual physical pages must be adjacent; the printed page numbers that both sides have read and that can be parsed must be continuous within the same system; the chapters must be the same; and by default the pair must be the actual last block/first block of the body text. If a real figure or caption lies between the continuation sentences, a decision reviewed against the source image may explicitly add `allow_intervening_figures:true`, which only permits skipping a figure/caption at the boundary and must not cross any paragraph/formula/heading/table or other body content; those figures and captions are still retained separately, counted exactly once, and the reading-order adjustment and the IDs of the intervening source blocks are recorded. Automatic candidates may inspect the last/first text block but are still not applied automatically. When a page such as a chapter opening actually prints no page number and `printed_page` is null/empty, only a decision reviewed against the real source image may explicitly add `allow_unknown_printed_page:true`; this does not fabricate a printed page number and must not bypass a real gap between known page numbers on both sides, different page-numbering systems, or an unparseable erroneous string. Unknown page numbers are still rejected by default. paragraph/formula may be merged; a formula requires `allow_nonparagraph:true`, and the same explicit flag also permits a truncated continuation of a left-side theorem/proof/example/exercise to join a right-side paragraph, keeping the left block's original type and not merging two different theorems/examples. Figures, headings, and tables remain independent; you may specify `action:link` to establish a reviewed cross-page relationship, or keep to retain the boundary. `separator` is at most two whitespace characters and must not introduce new text. Merging concatenates exactly from the original text, shifts styles only by Unicode character offsets, updates the combined text_sha256, and does not create new styles based on semantics. Final coverage, provenance, parent, hashes, and style ranges are verified again.

A footnote at the bottom of a long page must not be treated as the last body paragraph or determined automatically from the bbox. Use `--footnote-decisions /absolute/reviewed-footnotes.json` to specify the anchor, marker, and consecutive footnote blocks confirmed against the real source image:

```json
[{"anchor_block_id":"p0027-b005","marker":"①",
  "block_ids":["p0027-b016","p0027-b017"],
  "source_sha256":"current PDF hash","source_checked":true,
  "reason":"Viewed the native page directly and confirmed the footnote marker and the full body range",
  "evidence_image":"/absolute/native-source-page.png"}]
```

The anchor must contain exactly one identifiable instance of the marker, such as `<sup>①</sup>`; the first footnote block must begin with the same marker. Footnote blocks must be on the same physical page as the anchor, and their IDs must be consecutive in the original source-blocks order; a block must not be claimed twice, and another footnote anchor must not be swallowed into a footnote; unknown markers, non-consecutive/cross-page blocks, missing real evidence files, or hash mismatches are all rejected. Keep `evidence_image` and its actual SHA256 in review; do not infer a math or body-text type.

Footnote attribution happens before cross-page candidate generation. Footnote body text moves from the top-level reading into the anchor's `footnotes` list; each item keeps `marker`, `anchor_block_id`, `marker_start`/`marker_end` (Unicode indices into `anchor.text`), `marker_source_text`, the complete original reading `blocks`, and review. The anchor's text/styles are not changed; `sources`/`source_block_ids`/`source_styles` merge all footnote provenance, and `text_source_block_ids` lists only the source blocks that actually form the main text. Source-block coverage is checked exactly once by the top-level mapping; nested footnote body text, original type/text/styles/coordinates/hashes are verified separately; footnote provenance must not be concatenated directly into the anchor body text. source-blocks still retains the original blocks and order. When cross-page main text is merged, the right anchor's footnote marker indices shift with the Unicode offset, and the footnote body text is fully preserved. The LaTeX exporter uses these explicit anchors to generate native footnotes; formulas may remain display formulas; body text and footnotes are both rendered from the same JSONL, without changing the original text to remove markers or add answers.

The figure registry may be a list or `{source_sha256,figures:[...]}`; entries support `figure_id`/`id`, `physical_page`/`source.page`, `bbox_px`/`source.bbox_px`, `block_id`/`source_block_id`, `caption_block_id`, and the original book's `source_caption`/`printed_number`. First verify the PDF hash and original coordinates, then bind by explicit source block or by unique bbox IoU plus number association; keep the whole entry's `final_assets` (including latex paths relative to the book), and the LaTeX exporter verifies and references them. QR codes, cover logos, and similar items are bound the same way. Ambiguous matches, multiple figures claiming the same block, or no matching source image block all keep the original block and report `needs_review`; do not guess an asset and do not silently delete a block. A binding check does not mean the drawing content or asset rendering has passed acceptance.

An assemble exit code of 0 means structural and provenance accounting succeeded; `assembly-report.status=needs_review` still means explicit unresolved items remain. The report stores candidate/applied decisions, figure bindings, evidence downgrades, exactly-once source-block coverage, output hashes, and real timing. The three existing output files are not overwritten; rebuild into a new output directory, or handle the old artifacts separately after explicit review. LaTeX export uses the same blocks.jsonl and separately compiles, inspects the real rendering, and checks formulas/tables/styles against source images; no compile error does not mean the transcription is correct.

## Figure data

A figure block adds `figure_id`, linking it to the parallel figure list; the final referenced path is chosen by the coordinator and must not be written into the merged body text by individual models. The figure spec contains `id`, `source.pdf_sha256`/`page`/`bbox_px`/`page_size_px`/`page_size_pt`, `canvas.width_mm`/`height_mm`, `style_version`/`style_sha256`, `route`, `inputs`, and a context index. `page_size_pt` records only the PDF canvas and is not automatically the original paper size. Page-level correction stores the forward and inverse homography matrices for source/view, `view_bbox_px`, and the nominal paper width; the original crop and the corrected crop are kept separately.

`scene.json` stores in-figure `labels`, `objects`, `data`/`provenance`, `viewed_context_images`, and `uncertainties`; provenance is classified as source_formula/source_data/schematic_estimate, and only actual verification marks it as source-image confirmed. Each attempt keeps `draw.py`, optional `data.json`, the render spec, the shared style snapshot, output, and acceptance/feedback. `render-metadata.json` contains frozen dimensions, the size of the 400dpi reconstructed PNG, actual font/script/input-output hashes, and the vector/mixed/raster declaration. `retain_source` keeps the source image pixels and the actual effective DPI; the 400dpi reconstruction requirement does not apply to it.

The technical `review.json` does not evaluate semantics and is not grounds for `accepted`. The final `figures.json` separately stores the selected attempt or source-image fallback, `display_width_mm`/`display_height_mm`, relative PDF/SVG/PNG paths, provenance and data evidence, content/visual acceptance, and unresolved issues. Markdown/HTML and LaTeX reference the same asset at this display scale. For the complete directory, field usage, and model calls, see [Figure workflow](figures.md).

### Verified per-line numbered equation systems

`numbered_system` is an optional display contract: `schema_version=1`, `source_sha256`/`source_image_sha256`/`text_sha256`, complete `source_block_ids`, review containing `source_checked=true`, real `evidence_path`/`evidence_sha256`, and a reviewer; each `rows` entry contains `index`, the original math, and `source_number`. It is available only for a complete left-brace simple array with ordinary numbering that is continuous across rows in the same chapter; any change in row count, math content, original numbers, source IDs, image or text hashes is rejected. After verification, the exporter uses standard numcases/label and does not change the original text or raw canonical.

### Whole-book back-matter roles and algorithm indentation

The `document_parts.py` contract and `block.document_part` contain `part_id`/`role`/`pages`/`title`/`title_variants`/`columns` plus pinned `contract_path`/`contract_sha256`/`source_sha256`. Provenance evidence covers every page; back-* parts do not participate in body chapter numbering; the source and reading layers keep the text and unique ID. Two-column indexing is used only for a source-reviewed `role=index`, and the back cover must be separate. Algorithm `block.list_presentation` accepts only a flat list/paragraph, original text and image hashes, source IDs, and real source-image evidence; `indent_ccwd`/`hanging_ccwd` are Chinese-character-width paragraph parameters within a limited readable range, do not change step numbers or math, and nested items/footnotes must not be silently flattened. For specific styles and fields, see [LaTeX export](latex-export.md).

## Structure candidates and review metadata (schema_version=1)

Page OCR only produces candidates and does not fill in an independent `review.source_checked=true`. Model-reported confirmation is downgraded during normalization/assembly with the original value retained; a later real source-image review may provide the following presentations:

- `paragraph_presentation`: `boundary_before=continue/new_paragraph/unknown`, `first_line=inherit/indent/noindent`; `paragraph_id` and `predecessor_block_id`/`successor_block_id` may be used; `unknown` remains unresolved and must not automatically be treated as a new paragraph. A formula and the text before and after it each have their own provenance and original text.
- `heading_presentation`: `role` is chapter/section/subsection/subsubsection/part/document_title/unnumbered_heading/local_heading/algorithm_label, `font_size` is body/small_heading/chapter/section/subsection, and `indent_ccwd` is in 0..6. Numbered hierarchy is separate from local structure; local headings do not automatically enter the table of contents. A local numbering prefix may use `label_normalization={original,replacement,rule_id,rule_version}` for reading-layer width normalization: `original` must strictly match the text prefix, the Unicode length and numbering identity must be the same before and after replacement, and the original text/hash and style offsets are preserved.
- `list_presentation`: `kind=ordered/unordered/description/steps`; `indent_ccwd`, `outer_indent_ccwd`, `hanging_ccwd`, `labelsep_ccwd`, `labelwidth_ccwd`, and `item_indent_ccwd` are Chinese-character-width parameters within limits; `items` supports text/label/marker/styles/label_styles/children. `item.styles` are relative to `item.text`, and `label_styles` are relative to the Unicode range of the explicit label; for description, the gap between label and body is controlled by `label_body_gap_ccwd`. A source first-line indent with continuation lines returning to the text block can be expressed with `outer_indent_ccwd=0`/`hanging_ccwd=0` combined with `item_indent_ccwd`, without fabricating code-style spaces. bullet/●/• go through the template's native labelitemi to control size and avoid missing glyphs in the text font.
- Reading-layer list numbering normalization may use `list_presentation.label_normalizations=[{item_index,original,replacement,rule_id,rule_version}]`; the index is unique and `original` strictly equals the original `item.label`, `replacement` is non-empty and must preserve numbering identity (for example, `(1)` may become `（1）` or `1.`, but must not become `(999)`). Only the rendered label is replaced; the original text/items and hashes remain, and the sidecar records the change; do not apply full-width/half-width rules to formulas, code, or strings. A replacement of the same Unicode length preserves the original `label_styles` offsets; when the length changes, only styles that cover the entire label are projected automatically; if local style mapping is ambiguous, reject at the contract stage and never enter compilation with invalid offsets. description and other explicit labels all preserve `label_styles`.
- An unordered item may separately provide `marker`, `label`, and `text`, e.g. `{"marker":"•","label":"完整性","text":"说明正文"}`. The marker stays in the native item label box; the emphasized term stays in the item body, followed by the reviewed label/body gap. This applies to unordered lists as well as description lists; do not treat the term as the marker or drop an explicit source marker. Without a separate `marker` field, the existing explicit `label` remains the item marker, so input with custom numeric/symbol labels keeps its meaning.
- `code_presentation`: `language` and `completeness` are required; `outer_indent_ccwd`, `font_policy`, `wrap`/`wrap_policy`, `tabsize`, and similar fields are described in the code reference; `lines` must equal `text.splitlines`, and `source_line_ids` is unique per original line. `annotations` contain the owning block, original line range, and `label` or `label_block_id`.
- `grammar`: preserves the original text; it also has a native structure in `latex`/`native_latex` or `alternatives`, and rejects puzzles assembled from Unicode bracket parts; `display_group.groups` explicitly references each column's code/caption ID, column weight, and source order.

A reviewed presentation binds `source_sha256`/`source_image_sha256`/`text_sha256` and `source_block_ids`; review contains `source_checked=true`, a non-empty reviewer, and an actually existing `evidence_path`/`evidence_sha256`. Any hash or ownership change is rejected; the existence of evidence only proves that identity is traceable and cannot automatically prove that the review judgment is correct. Unreviewed candidates must not be used to render established relationships or to claim that the format passed. The presentation of a cross-page combined block stays in `source_semantics` and `merged_presentations`; do not relabel the first fragment's hash as the merged text; assembly rebuilds text/styles and verifies the snapshot, export verifies that `merged_presentations` equals the first source fragment's fields, and re-checks source/image/text hashes and actual review evidence against `sources`. Footnote child blocks go through the same semantic review and separation policy.

For the production-admission schema for format profile/ready, real artifact checks, and the restricted preflight mode, see [Format preflight](book-format-preflight.md). This does not require re-invoking historical OCR; reassembling/trial-typesetting existing data is enough to validate new structural capabilities, and historical results keep their original contract.

For the fields and boundaries of the production math-grouping sidecar and `--math-presentations`, see [LaTeX export](latex-export.md#source-reviewed-math-grouping); it is not the `display_group` for side-by-side code, and the capability declarations of the two must not be mixed. When an explicit list's effective rendered labels contain both ASCII (n) and full-width （n）, semantic_contract rejects them; after source-reviewed `label_normalizations`, export again; old flat text without an established semantic group still requires human/model screening, and you must not claim that this local validation covers it.

## Generic input and blank pages

`source_identity.py` defines source identity; `source.kind=pdf|image_collection`, `source.sha256` is the generic identity, and PDF compatibility retains `pdf_sha256`. Each consuming entry point's `--source` accepts a PDF or a fully numbered PNG directory; `--source-pdf` is a legacy alias. A collection identity does not include absolute paths; a change in the complete numbered set changes the identity, so you must not verify only the pages sampled in this run.

A genuinely blank page's page JSON uses `page_status="blank"`, `blank_reason`, and `blocks=[]`, and still submits all `viewed_images`; an ordinary page uses `page_status="content"` or omits it. assemble generates a source block with `type=blank`/`text=""` to retain coverage and does not fabricate text. Passing only `--rules` to the font library does not implicitly change styles; the explicit `--style-patches` accepts a font patch object or list of objects for this page, in the same format as above, with `scope` using lists of pages/types/chapter_ids. Confirmed styles are preserved; conflicts are rejected.

## Document-type-independent reviewed hierarchy

`heading_presentation` may have `depth` (integer 1..6) and `container_id` (non-empty stable identifier; `depth` must be given at the same time). They override chapter heuristics only after the existing `review.source_checked` and the source/text/image/evidence identity checks pass; unreviewed candidates are not applied. `container_id` is stored in the reading JSONL under the compatible field `chapter_id` and is not required to be chapter-N; for example, paper sections, appendices, or other document containers may use this run's stable ID. A new container resets the parent heading stack; body text/subheadings inherit the current container, and original titles and printed numbers are unchanged. When classification evidence is missing, the initial container is `unclassified`; do not call every page without a visible chapter number publication information. Conventional Arabic/Chinese chapters may still automatically produce structure candidates; numbering schemes that are not supported use this source-review entry point, without adding text rules for a single article.

Shared table parsing lives in `scripts/table_data.py`; evaluation and LaTeX use the same reader. `cells` supports a two-dimensional row array, or an explicit cell list with non-negative integer `row`/`col` (0-based; a non-conflicting `column` may be used); each cell has `text`, optional positive integer `rowspan`/`colspan`, and Unicode `styles`. Explicit coordinates do not guess the starting point, and mixing arrays/coordinates, overlaps, or holes is not allowed. Source data and order are not rewritten; it is sorted into a row view only when read. When `cells` must be revised, use a normalized patch with before/after and source evidence. Expressing table data does not prove that ruling lines, font size, font, or visual layout have been verified.

When there are no `cells`, HTML, pipe tables, and restricted literal LaTeX tabular are supported as read views; macros are not expanded, and complex nesting/cell spans/spacing commands require explicit `cells`. `text` always preserves the original expression. Ordinary extraction may retain unsupported original structures and list them as `needs_review`; production table export must not silently flatten them.

Source colors use `kind=color` with `value=#RRGGBB` and ordinary Unicode range/evidence fields; overlapping colors must agree. They record observed colors rather than a generated syntax theme. `grammar_lines` preserves literal rows and optional Unicode script-position ranges; see [Special text](code-special-text.md). `flow_presentation={schema_version:1,keep_with_next:true|false}` records an explicitly reviewed relationship with the next reading unit. It controls pagination, never reading order or merging; links cannot cross missing source pages. The exporter conservatively keeps short introductions with following formulas, grammar, or code for legacy data; an explicit false disables this heuristic.
